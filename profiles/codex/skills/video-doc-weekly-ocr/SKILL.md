# Video Document Weekly OCR

Use this workflow to reconstruct a weekly Markdown report from screen-recorded Feishu/Lark/Notion-like documents, especially videos containing numbered sections, blue links, embedded preview cards, and scrolling pages.

## Core Rules

- Prefer content accuracy over visual layout. Rebuild Markdown structure, not pixel-perfect formatting.
- Extract frames from the original videos at 1 fps, then select distinct scrolling/key frames before OCR.
- Keep OCR provenance: every uncertain title or URL must be traceable to a source frame/crop.
- Never treat a matching numbered-item count as proof of completeness. Unnumbered sections, progress text, quotes, preview cards, and trailing sections can still be missing.
- Do not publish short or partial Douyin links as usable links. A valid Douyin video URL must match `https://www.douyin.com/video/<19 digits>`.
- Do not delete partial links. Use them as search anchors, go back to the source frame, crop the blue-link line, and complete them when possible.
- In final user-facing Markdown, keep each item self-contained:
  - `确定链接：...` for the best/full link.
  - `备选链接：...；...` on the same item for plausible alternatives.
- Do not scatter `待核对` through the main document. Put review evidence in separate files.
- Blue text/link area is usually the URL; the title is the line immediately above it.
- If the source page shows a gray/quoted summary paragraph between an item title and its URL, preserve that paragraph as an item note in `document.md` and render it between the `<h3>` title and link row in Feishu.
- For design/tool/resource items with no visible link in the video, run source-page section link extraction before declaring the item unresolved. If multiple missing items map to the same source article or weekly page, parse that source page once and batch-fill every matching item from its headings and local link rows.
- Feishu preview cards are generated by Feishu after pasting/link-view selection; do not try to fake cards in Markdown. For paste output, put links on their own lines.
- When replicating into Feishu with `lark-cli`, keep item titles and links separate unless the user explicitly asks for title-as-link:
  - title line: numbered plain text;
  - next line: raw clickable URL only, without a `链接：` prefix;
  - next line if needed: `备选：<alternative URLs>`.
- Render section headings like the source screenshot: red heading text with a visible leading `#`, for example `# 搞钱`.
- Treat the left-side list in Feishu as the automatic document outline/sidebar unless the user explicitly asks for a visible in-body column. Do not recreate that sidebar as a manual table column.
- Replicate the final Feishu document as a heading hierarchy:
  - page title in `<title>`;
  - each report category as `<h2><span text-color="red"># Section</span></h2>`;
  - each numbered item title as `<h3><span text-color="blue">N.</span> Title</h3>`;
  - notes, raw URL rows, alternatives, bookmarks, and images immediately below the item heading.
- Avoid `<table>`/`<grid>` for the directory layout. They create a fake in-body sidebar and prevent Feishu's automatic outline from matching the original left navigation.
- Do not use `<ol><li>` for item numbering; use the visible blue number inside the `<h3>` so numbering and title text stay separate from the link row.
- Preserve numbering that is verified against the source outline, including intentional continuation across subsections or intentional jumps. Re-number only when source evidence proves an OCR duplicate/skip artifact; never force every subsection to restart at 1.
- Preserve source-visible section boundaries, even when the OCR report grouped items differently. For the 2026-07-07 weekly, the source screenshot separates `# 设计模块` from `# 工具与科技`; Reicon, Icones, LottieFiles, animation vocabulary, OpenPencil, and Grill-me belong under `# 工具与科技`.
- For the 2026-07-07 source screenshot, use the source title `且曼内刊 - Vol.283 20260707` and source-visible section order: `本周最TOP`, `AI热点`, `AI基础`, `设计模块`, `工具与科技`, `星期快讯`. Do not keep OCR artifact sections `AI视野` or `AI改变` in the Feishu replica unless later source evidence shows them.
- Do not rely on `readonly-block type="iframe"` for Feishu video previews. Fetch may show existing Douyin preview/player blocks, but `docs +create/+update` may drop them or Feishu may auto-convert only some links. Treat iframe previews as front-end-generated, not deterministic CLI output.
- For tool/resource detail items with multiple links, label rows by domain when the source shows labeled links:
  - official/project site: `网站: URL`;
  - Figma community/plugin: `Figma 插件: URL`;
  - GitHub repository: `Github: URL`.
- When the source screenshot shows a tool description or preview card, add the recovered description before link rows. Prefer inserting a stable preview image with `<img href="..." width="..."/>` when an official OG/preview image is available; also use `<bookmark name="..." href="..."></bookmark>` for clickable preview context.
- For article/resource items, keep source-visible summaries exactly enough to preserve meaning. Do not drop them during the "clean final document" pass just because they are not links.
- When the user permits sub-agents, split final cleanup into independent read-only audits: one agent for missing links across the whole document, one for domain-specific sections such as design. Keep the main agent responsible for final merge, source judgement, and validation.
- Rebuild the audit after every supplementation pass. Stop only after a fresh pass finds no new section, item, link, title correction, or duplicate.

```text
  frames_1s/part2/*.jpg

  ocr_work/ocr_raw.jsonl
  report/document.md
  report/document_feishu_paste.md
  report/document_with_review_notes.md
  report/review_items.md
  report/link_completion_fast/completion_results.md
```

## Workflow

1. Inspect videos with `ffprobe` and make a dedicated output directory.
2. Extract 1 fps frames with `ffmpeg`:
   `ffmpeg -hide_banner -nostdin -y -i input.mp4 -vf fps=1 -q:v 2 frames_1s/part/frame_%06d.jpg`
3. Select distinct frames using `scripts/select_weekly_keyframes.py` or equivalent visual-diff filtering. Threshold around `40`, min gap around `5`, worked well for 1080p Feishu screen recordings.
4. OCR selected frames. RapidOCR is fast enough for all selected frames. PaddleOCR is more accurate for Chinese but slow; use it for spot checks or small targeted crops, not full videos unless time allows.
5. Build a first report with source notes and review material. Preserve all uncertain URLs in a review-notes version.
6. Generate a clean final document from the review-notes version:
   - Merge complete links into the corresponding item.
   - Use `确定链接` and `备选链接` in the item itself.
   - Remove noisy per-line `待核对` from the main document.
7. Run partial-link completion. For every short Douyin candidate, crop the source frame around the blue link and OCR the crop. Replace short links only when a full 19-digit URL is recovered.
8. Run a second pass for section-specific gaps:
   - Re-audit sections that look too small, especially design/module sections.
   - Search OCR by title fragments loaded from `document.md`, not hardcoded Chinese strings in PowerShell commands.
   - For design/tool links, inspect nearby frames and OCR context first. If the video never exposes the URL, use web search only for exact title matches from credible sources, and treat those as web-supplemented links.
   - For design/tool/resource items that came from a source article or weekly page, find the source page and extract links by matching the item's heading or nearby heading text. Batch-process adjacent missing items from the same page instead of searching one by one. Example: Moonvy design weekly pages may contain `灵感网站推荐`, `Gradient Lab`, `Posts.design`, `Reicon`, and other tool sections with `官网`, `X 推文`, `GitHub`, or `Figma 插件` links directly under each heading.
   - Add missing independent items found in source frames, such as a design tool entry that appears in OCR but was skipped by the first report builder.
   - Remove page-header or volume-number pseudo-items that OCR promoted into numbered entries.
9. Validate final output:
   - Count short Douyin links; must be zero.
   - Check no local screenshot paths leaked into `document.md`.
   - Check `待核对` count in main document; should be zero or intentionally minimal.
   - Confirm `document_feishu_paste.md` was regenerated from final `document.md`.

## Mandatory Re-audit And Supplement Gate

Do not publish immediately after the first OCR build. Run this gate against the current week's videos only.

1. Build three inventories:
   - `outline_manifest`: every visible main section, subsection, numbered item, and unnumbered trailing line from the left outline;
   - `body_manifest`: every body title, summary, raw URL, embedded preview-card title, local attachment, quote, progress line, and image;
   - `report_manifest`: every section/item/link/image currently in `document.md`.
2. Diff the manifests by hierarchy, not only total count. Require an explanation for every outline/body entry missing from the report. A whole unnumbered section such as a news/progress block must not disappear merely because numbered counts match.
3. Re-scan the first and last 2-3 minutes of each part plus every section transition. Screen recordings often reveal the table of contents at the beginning and trailing sections near the end.
4. For each missing link, use this recovery order:
   - full URL visible in the owning source frame;
   - targeted multi-frame crop at 5-10 fps around the title/link row;
   - embedded preview-card title or provider metadata visible in the body;
   - build a metadata search tuple from every visible clue: exact title, creator/account, duration, publication date, and distinctive hashtags; run both exact-phrase and combined-field searches on the likely source platform;
   - exact-title provider/API lookup, such as Bilibili view/search API, official project page, or source publication;
   - matched source-page section extraction for design/tool/resource collections;
   - screenshot fallback only after the metadata search tuple and applicable provider/API searches have been attempted and logged, even when the source appears as a Feishu local upload;
   - unresolved only after all applicable stages fail.
5. Keep title roles separate:
   - `outline_title` controls directory placement and numbering;
   - `resource_title` is the exact linked page/video title;
   - if the difference is only punctuation, spacing, suffix, or OCR expansion, use the verified resource title;
   - if the outline title is generic, such as `AI大事件`, keep it as the item heading and add the exact preview-card title as a note with its recovered link.
6. Verify exact-title supplements before accepting them:
   - Bilibili: require a valid BV result and API `code=0`; compare the returned title;
   - article/tool page: compare the page title and section context, not only a search snippet;
   - Douyin: require exactly 19 digits and item ownership from source position or an exact public result.
7. Run duplicate checks across primary and alternative URLs:
   - normalized exact title duplicates;
   - high-similarity title pairs, then manual semantic review;
   - exact URL duplicates and collisions between primary/alternative links;
   - same URL attached to different titles, which requires source-ownership review.
8. Treat screenshots as a first-class fallback, not a missing link:
   - never infer that an original URL does not exist merely because Feishu displays the item as a local attachment;
   - record the exact search queries, platforms checked, and rejected candidates before assigning `screenshot_fallback`;
   - create one item-owned crop per fallback; never reuse a whole-page or outline screenshot under multiple items;
   - crop tightly around the owning title/link/card region. Include an adjacent row only when it proves ownership or link state, and explain why;
   - save it under `report/assets/`;
   - insert it directly below the corresponding item;
   - add a visible review note containing the source part, exact `HH:MM:SS` timestamp, what the crop proves, and what it does not prove;
   - title-only/outline evidence proves only the title and source link state. It must explicitly say `不作为链接证据` and must never be presented as a recovered URL;
   - use unique, traceable names such as `review_<item-number-or-slug>.jpg`; keep the original source frame, crop rectangle, and search status in `missing_audit.md` or a structured evidence manifest;
   - count it as `screenshot_fallback`, not `linked` and not `unresolved`.
9. Regenerate `missing_audit.md` from current structured data. It must report:
   - total items;
   - primary links;
   - alternative links;
   - screenshot fallbacks;
   - unresolved items;
   - exact/high-similarity title duplicates;
   - URL duplicates/collisions;
   - malformed Douyin links;
   - source frames for every correction or fallback.
10. Repeat the diff and validation once after corrections. A clean second pass is the completion condition.

## Feishu CLI Replication Workflow

Use this when the user has recreated or wants to recreate the report in Feishu/Lark and asks for the weekly format to match the source document.

1. Ensure `document.md` is final first:
   - no short Douyin links;
   - no local path leaks;
   - confirmed and alternative links are under the same item;
   - main doc has no noisy review notes.
2. Generate Feishu XML:
   ```bash
   python scripts/make_feishu_weekly_xml.py report/document.md report/feishu_ready.xml \
     --media-manifest report/feishu_media_manifest.json
   ```
3. Inspect the XML head before writing:
   - final Feishu XML should start with `<title>`, then use `<h2>` section headings and `<h3>` item headings;
   - the left directory is Feishu's automatic page outline/sidebar generated from headings, not document content;
   - item title should be `<h3><span text-color="blue">N.</span> Title</h3>`, not `<li>`;
   - section heading should be `<h2><span text-color="red"># 章节名</span></h2>`;
   - link should be a following `<p><a href="...">...</a></p>` without a `链接：` prefix;
   - multi-link tool details may use labeled rows such as `网站:`, `Figma 插件:`, `Github:`;
   - alternatives should be `<p><span text-color="gray">备选：</span>...</p>`.
4. Create a small test Feishu document before touching the user's target doc when the format changed:
   ```bash
   lark-cli docs +create --api-version v2 --as user --content "@report/feishu_ready.xml"
   ```
   Fetch it back and verify section count, list count, and link count.
5. Overwrite the target only when the user has asked to apply the format:
   ```bash
   lark-cli docs +update --api-version v2 --as user \
     --doc "<feishu-doc-url-or-token>" \
     --command overwrite \
     --content "@report/feishu_ready.xml"
   ```
6. Fetch the target back and validate:
   - section names and item headings appear in Feishu's outline fetch;
   - document content does not contain a fake two-column directory table/grid;
   - every section has continuous heading numbering from `1..N`;
   - no visible layout item is rendered as `<ol><li>`;
   - link rows contain raw clickable URLs;
   - `readonly-block` count is not used as a success criterion.
7. Preserve real hierarchy when the source has subsections:
   - main section: red `h2` with visible `#`;
   - subsection: `h3`;
   - item: blue-numbered `h4` under a subsection, otherwise blue-numbered `h3`.
8. Render summaries as gray paragraphs. Do not use unsupported `<quote>` tags; some CLI versions escape them into visible text.
9. Insert local fallback images after document creation:
   - create/overwrite the text structure first;
   - use `docs +media-insert` with the local image;
   - fetch the target item heading with block IDs;
   - use `block_move_after` to place the image immediately below that heading;
   - insert the item-specific review paragraph immediately after the image;
   - fetch again and verify the exact order is `owning heading -> matching image -> matching review note -> next item`;
   - verify every fallback image filename is unique, no old generic/whole-page image remains, and the fetched image name matches the local evidence manifest;
   - do not report publishing complete from successful upload alone; the post-publish block-order fetch is mandatory.
10. Place the document in the user-specified Drive folder instead of assuming the root directory:
   - resolve the folder token with `drive +search` or a supplied folder URL;
   - create the document, then `drive +move --type docx --folder-token ...` when needed;
   - verify with folder-scoped search or `drive files list`;
   - allow for search-index delay and retry after several seconds before declaring failure.

### PowerShell-Safe Local Feishu Updates

Use this for targeted link insertion or correction in an existing Feishu document. Prefer local block updates over full-document overwrite when the user asks to preserve screenshots, manual edits, and existing layout.

1. Fetch the target item and copy its exact heading block ID. Insert the URL after the owning title block; never append links at the document end or bind them by nearest timestamp alone.
2. Keep title and link as separate blocks. A preview link row should use valid XML such as:
   ```xml
   <p><a type="url-preview" href="https://example.com">https://example.com</a></p>
   ```
3. Do not pass XML with quoted attributes inline through PowerShell. Shell parsing may strip quotes and produce invalid XML such as `<a type=url-preview href=https://...>`.
4. Write each payload to a UTF-8 file without BOM, then pass it with `--content '@payload.xml'`:
   ```powershell
   $xml = '<p><a type="url-preview" href="https://example.com">https://example.com</a></p>'
   [System.IO.File]::WriteAllText(
     (Join-Path $PWD 'payload.xml'),
     $xml,
     [System.Text.UTF8Encoding]::new($false)
   )

   lark-cli docs +update `
     --doc '<DOC_TOKEN>' `
     --command block_insert_after `
     --block-id '<TITLE_BLOCK_ID>' `
     --content '@payload.xml'
   ```
5. Run the same request with `--dry-run` first when available. Inspect the serialized request and confirm the XML attribute quotes remain intact.
6. Treat CLI transport success and document mutation success as different states. Require all of the following:
   - top-level command did not error;
   - `data.result == "success"` or the equivalent mutation result is successful;
   - warnings/degrade messages are empty;
   - document revision increased;
   - a post-update fetch shows the URL directly below the owning title.
7. `ok: true` alone is insufficient. XML tokenization errors, instruction validation failures, or an unchanged revision mean the write failed even if the wrapper returned success.
8. Preserve item-owned screenshots and manual notes. Do not use overwrite merely to add links. Delete temporary payload files only after the post-update fetch passes.

Validation snippet:

```python
import json, re, html
from pathlib import Path
c = json.loads(Path("report/feishu_target_after_update.json").read_text(encoding="utf-8-sig"))["data"]["document"]["content"]
assert "链接：" not in c
assert "<table" not in c and "<grid" not in c
assert "<h2" in c and "<h3" in c
assert "<ol" not in c and "<li" not in c
assert re.search(r'<h2[^>]*><span[^>]*text-color="[^"]*red[^"]*"[^>]*># ', c)
assert re.search(r'<h3[^>]*><span[^>]*text-color="[^"]*blue[^"]*"[^>]*>1\\.</span> ', c)
```

## Link Handling Rules

Classify links as follows:

- Confirmed Douyin: `https://www.douyin.com/video/` followed by exactly 19 digits.
- Confirmed external: trusted full links such as GitHub, woshipm, mp.weixin.qq.com, zhihu, x.com, ifanr, reicon.dev, beui.dev, lottiefiles.com, openpencil.dev, figma.com/community, and source articles with exact title matches.
- Alternative: plausible full external links or multiple full links near the same title.
- Partial: short Douyin fragments such as `/video/765557`, OCR-domain variants such as `douyir`, or malformed schemes like `hltps`. Never publish these as clickable final links. Use them to complete the link.

If OCR produces multiple full links near one item, put the best/nearest as `确定链接` and the rest as `备选链接` on the same item.

Web supplementation rules:

- Do not use web search to invent links for vague Douyin titles; if the video/OCR only shows a short Douyin fragment, leave the item linkless in `document.md` and list it in `missing_audit.md`.
- Use web search for external articles/tools only when the title is distinctive and the result title or snippet exactly matches the recovered document title.
- Prefer official/project pages for tools and source publications for articles. Examples: LottieFiles plugin pages, OpenPencil official site/GitHub, Reicon official/GitHub/Figma community page, woshipm article pages.
- When a search result is a source article or weekly page that contains several recovered titles, open that page and extract the links section-by-section. Use the heading text to bind links to the correct item, keep labels such as `官网`, `X 推文`, `GitHub`, `Figma 插件`, and include all links under that item.
- For source-page extraction, do not take the nearest arbitrary URL from the whole page. Use only links inside the matched heading's section, stopping before the next same-level heading. If two headings are adjacent and both missing links, process both from the same parsed page.
- If a link came from web supplementation instead of the video frame, mention that in the final response or an audit note when precision matters.
- When local OCR evidence and web search disagree, prefer the source-frame/video evidence if it yields a complete valid link. Use web search mainly to supplement items where local evidence is incomplete or absent.
- Do not override local source-frame ownership with a merely similar web result. If the visible link is vertically tied to the next item, keep it with the next item even if web search finds a plausible link for the previous generic title.
- For duplicate titles appearing in multiple sections, reuse the same confirmed link only when the title is semantically identical and the surrounding section context supports the duplicate.

## Targeted Final Link Recovery

Use this when only a few items remain unresolved after the normal link-completion pass:

1. Parse unresolved items from `document.md` or `missing_audit.md`.
2. Search `ocr_raw.jsonl` by title fragments read from the file. Record:
   - section/title,
   - `part`,
   - second,
   - source frame,
   - title-line box,
   - nearby URL-like line boxes and OCR text.
3. If original videos are still available, return to them before web search and extract only the relevant windows around the source seconds:
   - first pass: `second - 10~15` through `second + 10~15`, at `3-5 fps`;
   - difficult pass: expand to `second - 60~90` through `second + 60~90` when the first pass shows only the outline, an adjacent item, or a partially exposed card;
   - crop the title, blue-link line, card metadata, creator, duration, and platform area separately when full-frame OCR is noisy;
   - keep the exact frame timestamp and crop coordinates in the recovery notes.
4. If original videos are unavailable, fall back to nearby `frames_1s` crops. This is weaker but can still recover full links when the selected frame was just blurry.
5. Run RapidOCR first on enlarged/sharpened crops. Use PaddleOCR only for small crop spot checks if RapidOCR is inconclusive.
6. Accept a recovered Douyin link only when it is exactly 19 digits. Accept external links when the domain and path are complete and match the title context.
7. Write a compact evidence file such as `targeted_link_recovery_notes.md` describing each added link and whether it came from local OCR or web supplementation.
8. Leave generic heading-like entries unresolved if no independent link is visible. For example, a short title such as `AI大事件` may be a subsection marker, and a visible link far below it may actually belong to the next numbered item.
9. In the final response, explicitly separate:
   - links recovered from local targeted OCR,
   - links recovered from public title search,
   - unresolved generic/heading-like entries intentionally left blank.
10. If only one unresolved item remains and it is generic, do not chase diminishing returns unless the user has the original Feishu/Lark document or wants manual web investigation.

### Temporal Window Recovery Rules

- A single marked frame is only a starting point. Scrolling, hover previews, and card expansion often expose the owning URL several seconds before or after the title.
- Inspect every frame in the targeted window for the title, raw URL, creator/account, duration, publication date, cover subject, platform chrome, and neighboring item boundaries.
- If only the table of contents is visible, treat it as title/number evidence only. It cannot establish URL ownership.
- Do not bind a nearby URL to an item because it is temporally closest. Confirm that the URL and title/card occupy the same owning region or that metadata closes the match.
- Prefer original-video recovery over public search. Several valid links may be recoverable locally even when exact-title search fails.
- Re-run targeted OCR on enlarged, sharpened crops. PaddleOCR is appropriate for a small difficult crop even when RapidOCR handled the bulk pass.

### Evidence Closure Matrix

For every supplemented link, record and compare these fields:

| Evidence field | Strong signal |
| --- | --- |
| Source-frame URL | Complete URL visibly owned by the item |
| Title | Exact title or documented editorial rewrite |
| Creator/account | Matches the preview card or source frame |
| Duration | Exact or near-exact video duration |
| Cover/scene | Distinctive people, objects, captions, or event |
| Publication date | Compatible with the weekly time range |
| Body topic/entities | Names, products, places, counts, or claims match |

- Accept a link when the source frame directly exposes the full owned URL, or when multiple independent strong fields form a clear evidence closure.
- For Bilibili, a valid BV result plus matching title and at least one of creator, duration, or cover is normally sufficient.
- For Douyin, require a complete 19-digit video ID and item ownership; a valid-looking ID without ownership is not enough.
- For articles/tools, require the page title and section/body context to match. A search snippet or broad topic similarity is insufficient.
- Reject candidates that share only a theme. Record why they were rejected so later passes do not repeat the same false match.

Run the deterministic audit before final publishing:

```bash
python scripts/audit_weekly_report.py report/document.md \
  --json-output report/audit_structured.json \
  --markdown-output report/audit_structured.md
```

## Mandatory Deep Search Before Screenshot Fallback

Do not mark an item as `screenshot_fallback` after a shallow exact-title search. The 2026-08-11 recovery showed that valid Bilibili sources may appear below the first five results, use an OCR spelling variant, or use an editor-rewritten outline title.

1. Search each distinctive missing title with at least these variants:
   - the full outline title;
   - the longest distinctive phrase without punctuation;
   - creator/account name plus title keywords when a preview card exposes the account;
   - title plus visible duration, product, person, location, or object clues;
   - corrected OCR variants for obvious terms such as `Xbox` versus `Xioox`.
2. For Bilibili, request at least 20-30 results before declaring no match. A result is confirmed when at least two strong fields agree; prefer three or four:
   - title or a clearly attributable editorial rewrite;
   - uploader/account;
   - exact duration;
   - preview-frame subject or visible objects.
3. When the weekly outline rewrites a resource title, preserve both roles:
   - keep the weekly `outline_title` as the numbered heading;
   - attach the verified `resource_url` when the creator, duration, entities, and event establish the match;
   - record the original resource title and why the rewrite is considered equivalent in the supplement evidence.
4. A same-title repost without matching account evidence is not automatically the original. Put the best-supported result and repost alternatives on the same item, and retain the source screenshot for review.
5. For official tools and resource sites, verify quantitative or feature clues from the source body. Example: Koboyo was confirmed by the official site and the exact `71,262` icon count, not by title similarity alone.
6. Resolve apparent time-window URL candidates before using them. Open the candidate page and compare its returned title; a nearby URL may belong to the preceding or following item. The 2026-08-11 Douyin candidate near item 30 actually belonged to item 31.
7. Log the search depth and rejection reason for every remaining fallback. The final missing audit should distinguish:
   - generic titles with insufficient metadata;
   - outline-only personal text that is not publicly indexed;
   - exact-title results rejected because account, duration, or content did not match;
   - genuinely exhausted searches.
8. After this deep pass, rebuild the report and require zero duplicate URLs, zero duplicate normalized titles, and unchanged numbered-item counts before publishing or updating Feishu.

## Authenticated Platform Rate-Limit Circuit Breaker

Treat logged-in social-platform search as a shared, rate-limited resource across the main agent and all subagents.

1. Never run concurrent searches against the same authenticated platform/session. Xiaohongshu searches are serial by default, with at least 2-3 seconds between ordinary requests and a longer interval for repeated deep searches.
2. Keep one platform request queue for the whole task. Delegating to subagents does not create independent rate-limit budgets.
3. On any captcha, `请求太频繁`, `AUTH_REQUIRED`, login challenge, or equivalent anti-abuse response:
   - stop all new requests to that platform immediately;
   - notify every active subagent that the platform is in cooldown;
   - do not refresh, retry, open detail/comment endpoints, or switch agents to continue the same search;
   - preserve already collected read-only results and continue with original-video evidence, other public providers, and ordinary web pages.
4. Record the platform, trigger time, last successful query, and cooldown state in recovery notes without recording cookies or tokens.
5. Resume only after a meaningful cooldown and explicit task need. Test with one low-frequency query first; if the warning returns, re-enter global cooldown immediately.
6. A message such as “一分钟后再试” is not permission for automated polling. Do not schedule repeated retries.

## Lessons From 2026-06-30 Weekly Recovery

Use these extra rules when a user gives a new week's videos and asks to "continue", "补全", or "按之前流程做":

1. Treat each weekly reconstruction as a fresh dataset unless the user explicitly asks to reuse old output. Do not use previous `reconstructed_doc_*`, old `selected_frames`, old OCR JSONL, or older report files as content sources for a new week's final document. Old files may be used only as workflow examples.
2. Record the exact OCR source in `missing_audit.md`, for example `weekly_YYYY_MM_DD/ocr_work/rapid_ocr_raw_merged.jsonl`, and validate that the final document does not contain paths from older weekly directories.
3. If the user says "不要用老的数据", immediately delete old-derived assumptions from the current reasoning and rerun extraction/OCR/build from the latest provided videos.
4. Never fill links only by temporal nearness when the source frame shows that the blue URL belongs to the next item. A title without a visible URL should remain unresolved or be supplemented only by exact public title search.
5. When a visible frame has the title on one line and a blue URL line below, bind that URL to the item only if there is no intervening next numbered title. If a new item title appears between them, the URL belongs to the lower item.
6. Bad or partial Douyin links must be completed, not deleted. However, completion requires either a valid 19-digit video id from source-frame OCR/crop or an exact public result. Do not publish `douyin.com/video/` fragments.
7. Use exact-title web supplementation for distinctive items only. Accept sources such as official sites, Bilibili, YouTube, CCTV, woshipm, ifanr, Juejin, GitHub, Figma Community, and project pages when the result title/snippet clearly matches the recovered title.
8. Leave generic headings unresolved instead of inventing links. Examples include `AI大事件`, vague category names, or outline-only lines that do not look like independent resources.
9. For OCR-garbled titles, first search nearby frames and crop around the line. If the title remains semantically unreadable, keep it in `missing_audit.md` instead of attaching a plausible but unverified URL.
10. For duplicated titles across sections, deduplicate only after checking section context. If the same item appears twice because of scroll/outline capture, keep the intended section and remove the duplicate; if it is intentionally repeated, reuse the confirmed link only when the surrounding text supports it.
11. After every supplement pass, rebuild `missing_audit.md` from the current `document.md`; do not manually maintain unresolved counts.
12. Final validation must include:
    - total item count and confirmed-link count;
    - unresolved item list;
    - zero short/overlong Douyin links;
    - no local source paths in `document.md`;
    - no noisy `待核对` or `链接待补全` markers in the clean document;
    - explicit note that old weekly OCR/report data was not used.

For this workflow, "补全" means:

- add confirmed links where source-frame OCR, targeted crops, or exact public search supports them;
- keep one clean best link on the item, with alternatives on the same item when needed;
- keep unresolved-but-real items visible in `missing_audit.md`;
- avoid reducing the report by deleting hard cases.

## Common Failure Modes

- PowerShell may display UTF-8 Chinese as mojibake. Verify file content with Python `repr` before assuming files are corrupt.
- OCR may mistake page headers such as `2026`, `Vol.xxx`, or timestamps as numbered items (`202.`, `207.`). Filter these from final documents.
- OCR may concatenate source paths or multiple URLs. Remove local paths from final docs and split joined links.
- Full-page OCR may attach a link to the wrong title. Prefer links that are vertically closest to the title in the same frame/crop.
- PaddleOCR on Windows may fail with oneDNN/MKLDNN. Set `FLAGS_use_mkldnn=0`, `PADDLE_DISABLE_MKLDNN=1`, and pass `enable_mkldnn=False`.
- Hardcoding Chinese text in a PowerShell here-string may produce mojibake. For matching titles, parse titles directly from UTF-8 files with Python, or use Unicode escapes for fixed labels such as `确定链接：` and `备选链接：`.
- Full-page OCR can miss design links that appear only in left outline or briefly during scroll. Recheck nearby 1 fps frames around the section, not only selected keyframes.
- Some lines in a section may be visible only as outline/table-of-contents entries. Do not assume every outline entry has a visible link in the video.
- A screenshot can be visually related yet still be invalid evidence. Reusing the same full-page outline image for several fallback items prevents manual verification and falsely implies link ownership. Require item-level crops and explicit evidence boundaries.
- A crop that shows only black outline text is `title_only` evidence. It may confirm wording/numbering and absence of a visible outline link, but it cannot prove that no source URL exists elsewhere in the body or on the web.
- A Feishu media upload may succeed while the image remains at the document end. Always move it under its owning heading, insert the timestamped review note, delete superseded images, and fetch the local section again.


## Final Audit And Regrouping

Before final delivery, run a section-level audit instead of trusting the first generated grouping. Screen recordings often show section headers on one frame and later items on later frames, so OCR may attach items to the next visible section.

Audit requirements:

- Count items and linked items per section.
- List every item that has no `确定链接` or `备选链接`.
- Compare current titles against the review-notes/original OCR version. A title may look missing only because it was rewritten more completely; verify semantically before adding duplicates.
- Check domain-specific misplaced items. For this weekly format, design items such as Figma, LottieFiles, animation, Icones, mechanical structure, Landing Page, OpenPencil, Reicon, and design workflow usually belong under `设计模块`, not `AI基础` or `AI改变`.
- Remove OCR page-header pseudo-items such as `202.`, `207.`, `2001...`, `Vol...`, or timestamp/volume fragments.
- Keep the main document clean, but write a compact `missing_audit.md` listing section counts, items still without links, and quality checks.

If a user asks what is still missing, answer from `missing_audit.md`: distinguish (1) true missing items, (2) items present under rewritten titles, (3) titles present but still missing reliable links.
