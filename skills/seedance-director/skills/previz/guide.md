name: previz
description: 当用户想在花钱生成之前先看看画面大概是什么样，说"能不能先看看效果/画个草图/这条动起来什么样/这几个人站位对不对/宫格长什么样/这个环绕镜头绕出来是什么效果"时使用；表确认与编译落盘两处也可由你主动提议。把已写死的镜头表翻成一份三维场景 JSON，交 previz.py 渲成导演台风格的三维 HTML 草图——动态放映 / 宫格 / 关键帧 / 站位图 / 场记平面图 / 接缝检查六模式，自带越轴、数据健康、接缝三项自检，导出 PNG 可作参考图。产出 .previz/ 下的场景 JSON 与 HTML；可选、不设门禁、不进交付。

[任务]
    把一条已落表的镜头翻成一份三维场景 JSON，用渲染引擎渲成 HTML 草图，交用户在花钱生成之前对齐"你和我脑中是不是同一个画面"。
    命令唯一，全部能力都在这一行里：

        python3 previz.py <场景.json> -m play|grid|keyframes|plan|stage|cut [-o <输出.html>] [--cols N]

    不给 -o 时引擎写到 `<场景 JSON 同名>.<模式>.html`，六模式可并存，这就是默认落盘形态。
    **场景是三维的，这是本站唯一的真相源。** 一份场景数据，透视投影出监视器画面、正交投影出俯视图，两者不可能对不上——因为它们是同一个空间的两次投影，不是两份各自维护的画。环绕、复杂转场这类二维画不出来的运镜，因此也画得出来了。
    本站只做翻译与落盘，一个字都不改镜头表——镜头表怎么写，草图就怎么画。写得含糊，草图就画得含糊，那正是要看见的东西。
    永远可选：不设门禁，草图不通过不阻塞任何一步；用户说了批量连跑就静默跳过，不提、不问。

[第一性原则]
    本环节是【导演思维】第 2 问「画面化」的展开：把画面层这份中间表示投影成看得见的东西，让人当场确认"意图 → 画面"这一次翻译落没落对。

    1 · 只渲染写死的东西。构图、站位、走位、运镜、时长节奏、台词时点——这六样镜头表里有原文，草图照搬即可，搬错了是本站的错。光线氛围、表演、材质质感一律不渲染：草图给不出，给了会误导——用户会拿一个白模人像的"表情"去评判一条还没生成的戏——白模没有表情，那是它的形态不是它的判断。
    立体只是让空间关系可读，不是让画面变真。三维带来的真实遮挡与真实透视都属于"空间关系"，不属于"画面质感"；越像成片，越要守住这条边界。

    2 · 不是生成。草图是代码画的示意图，不调用任何生成模型，不占用户一次额度、不进平台。这与 CLAUDE.md [角色] 的"不生图、不生视频、不生音频"不冲突——那条管的是不替用户去调生成模型，不是禁止用代码画示意图。

    3 · 导出的图可以当参考图投喂，但要过三道门。宫格图控构图序列，站位图控站位与轴线，导出即短边 1080 的 PNG。三道门是 control-image 的既有防渗规则，本站只读引用、不新立：帧类控制图必须嵌 visual-style 的通用基准段与场域锚句，草图没有；站位图必须白底细轮廓、无填充、图上零文字，草图是灰底三维白模渲染带中文标签；俯视规划图按 spatial-map-template 现行规则标"人用规划 · 勿投喂"。未过门的导出图只当给人看的沟通稿与写控制图提示词时的构图依据，不进条头【上传清单】、不被【参考资产绑定】@。
    代码画的站位精度天然高于生成——它能否替代要花一次生成的站位控制图，是[待验清单]里的实测项，实测出结果前不动 control-image 的选型设计。

    4 · 不设门禁、不进交付。草图永远是可选项：不通过不构成任何阻塞，产物不进记忆层、不进提示词包、不进任何审核报告。表确认与编译落盘两处可以主动提议一句"要不要先看眼草图"，但只提议不代做——用户要才做，批量连跑连提都不提。

    5 · 草图丑不等于提示词错，草图顺眼不等于成片稳。前半句防的是拿白模的美观度否掉一条好提示词；后半句防的是拿一张对齐的草图当质量背书——草图验证的是空间与节奏这两件代码算得准的事，模型的表演、光、质感它一个字都没说。

    判据全在 references/scene-data-method.md，按字段查对应判据卡，不照抄流程。

[认交付物选模式]
        问一句"要预览哪个交付物"，按下表选，不发明新模式：
            视频条提示词——看节奏、镜序、走位、运镜，附可自由环视的导演视图 → play
            宫格控制图——画面就是那张宫格图本身的样子 → grid，`--cols` 给列数
            关键帧序列控制图，只有一帧时即单张分镜 → keyframes，帧间标该帧到下一帧的时长
            站位图控制图——交付物本身：只画谁在哪、朝向哪、走去哪 → plan
            审全场覆盖——机位分布、每台机器拍到多宽、哪块没人拍 → stage
            审接缝——相邻两镜之间越没越轴、会不会读成跳切 → cut
        后两个是工作视图，给导演自己看的，不对应任何交付物。同一份 JSON 六模式都能渲，选错了重跑一次即可，不必改数据。

[抽数据 · 只搬镜头表已有的]
        场级空间地图块 → figures 的站位、身高、姿态（蹲 / 坐 / 跪 / 卧写 pose，抱物、抬手写 arms）、朝向与视线，axis 的轴线两端（人、焦点物、带 id 的陈设，或直接写点），solids 的陈设体块（按 kind 词表认：猫狗写 animal、水缸写 vat、认不出的写 block），focus 的视觉焦点小物。
        逐镜六字段 → shots 的 framing / fov / dur / pace / beat；【镜头语言】原文整句抄进 lens 字段，页面并排显示以便核对翻译。镜头表在某一镜里改了姿态或视线（站直、回头看窗）写进该镜的 figures 覆盖；表里标了轴上镜 / 骑轴中性镜的写 onAxis: true。
        【导演意图】的情感行压成一句进 intent。
        缺的标注不猜，见 [依赖检测] 末条。

[定坐标 · 只有一套]
        世界是 0–100 的三维网格：**x 左右、y 高度（0 就是地面）、z 进深（大 = 靠近默认机位一侧）**。所有东西——陈设、人、小物、摄影机——都写在这一套坐标里，没有第二套。
        二维版那两套互相要人工对齐的坐标系已经不存在了：俯视图与监视器画面是同一份数据的两次投影，对不上在物理上就不可能，不必再检查。
        先按空间地图块的"居 frame-left/right""高出半头""相隔一张球台的台面宽度"定相对量，不追求写实比例——草图要的是关系正确，不是尺寸正确。
        身高写进 figures.h，站立面高度写进 stand。**stand 是真实的台阶或踏板高度，不是纵深**——纵深是 p[2]，各归各的字段。

[翻运镜 · 顺序不许反]
        读【镜头语言】字段的运镜描述，译成摄影机数据。摄影机有且只有三种形态：
            静止——写 `cam` 机位、`look` 看点、`fov` 视场角，三样定死一个画面。
            两点插值——在静止的基础上加 `to` / `lookTo` / `fovTo`，机位、看点、视场角各自从起点走到终点；速度质感落 `moveEase`。推拉是 fov 或 cam 变，摇是 look 变，横移升降是 cam 变——这些不再是三种特例，是同一套插值的不同分量在动。
            环绕——写 `orbit{center, r, from, to, y}` 加 `look`，摄影机沿一段圆弧绕着 center 走。**这一类二维画不出来**，它是三维化的直接理由。
        镜头表写"锁定机位"就只写 cam / look / fov，不写任何 to，让它静止。
        方向永远是镜头表 → 草图。不许先在草图里挑一个好看的运镜，再回头改镜头表——那是拿投影反过来改真相源，画面层的所有权在镜头表不在这里。想改运镜，回 shot-design 改表，再重渲草图。

[渲染形态 · 导演台三维白模]
    引擎按导演台风格的三维白模渲染：浏览器里 WebGL 实时出图，一盏工作室灯（主光 + 补光 + 环境光）带真实投影，地面网格给距离参照。人是关节人偶——头、躯干、四肢、脚，躯干朝 facing、头看 gaze，走位时摆腿，pose 给蹲坐跪卧俯卧，arms 给抱胸背手叉腰指；陈设按 kind 词表拼成预制件（柜台、桌椅、沙发、床、柜、窗、门、门帘、木栅、柱、楼梯、屏幕、灯、盆栽、树、车、车内舱、路灯、镜子、相框、地毯、石、水缸、动物等，常用叫法有别名表），焦点物画成有形的小物件；词表没有的东西用 sphere / cylinder / cone / dome / fog / water / statue 这些基元配 tone、opacity、glow 拼出来，不写 block 凑数。play 模式多一个可自由环视的导演视图，看得见全部机位、取景锥、运镜轨迹、轴线、视线与走位箭头。三件事由引擎自己定，场景 JSON 不写、也写不了：
        - 灯是引擎定死的常数，**只为分清体块与遮挡关系，不是布光**。人物与物件不许各亮各的。
        - 颜色按 tone 生成，词表见引擎的 TONE；solids 的 kind 词表见 SOLID_KINDS，figures 的 pose / arms 词表见 POSES / ARMS，词表外的值会按灰盒子或站姿画并在自检里报出来。人物用哪个色调与控制图站位图同源，别另起一套。
        - 白模只表示体量、姿态、朝向与遮挡，不表示布光、材质与表情。看着"光打得不错"是工作室灯的副产物，不是本条的光影氛围字段——那个字段在草图里不渲染，归分镜图阶段。**立体、精细了，边界一条没松：越像成片，越要守住。**

[渲染与三项自检]
        跑命令，把终端输出逐条读完——三项自检是本站精准度的全部来源：
            数据健康，分两档：
                标 [拦下] 的是会让引擎崩的写法——坐标位留着占位符或字符串。**拦在渲染之前，退出码 2，已有产物一个字不动**，好过甩一段 traceback 或毁掉上一次的好草图。
                不标的是提醒——kind 不在词表、两人以上没声明 axis、某镜缺 look 或缺 fov。这些照样渲得出图，但那张图是错的、或另外两项自检在空转。**"没报错"不等于"全绿"**，所以它必须主动报。
            轴线检查：叉积算每个机位在 180° 轴线哪一侧，异侧即越轴，场记平面图标红 + 页面给结论。
            接缝检查：相邻两镜在被摄者处张开的夹角，低于 30° 会被读成跳切。三条豁免——切入的是运动镜（运动本身打断读感）、景别跨两档以上（尺寸变化本身即区分）、或两镜看的不是同一个被摄者（换了主体不算跳）。**这个数二维算不出来**：二维没有摄影机，只有裁切窗。
        报错回哪一站：数据健康 → 就在本站补数据，它报的是这份 JSON 写漏了，不是镜头表错了；越轴 → 回 shot-design 改机位，或按 blocking 的四条合法越轴路径走一条并把越轴写进场级空间地图块的「排布变化」行；接缝过小 → 回 shot-design 调机位角度或调景别差，两者改一样即可。
        **除数据健康外，草图报错指向的是镜头表的问题，不是草图的问题。** 改 JSON 把警告消掉是篡改证据——把机位挪回轴同侧，成片照样越轴。
        二维时代那两项自检已经消失，不必再找：裁切窗越界没有了，画框由 fov 与机位推出，不存在越界；焦段与机位一致性也没有了，视场角物理上就是真的，不需要检查。
        一项自动处理不必手工做：`cam` → `to`、`look` → `lookTo`、`fov` → `fovTo` 在镜内按 moveEase 插值，这是运镜。反打也不再需要处理——换个机位自然就是反打，二维那个整幅翻转的 hack 随坐标系一起消失了。

[落盘并交付]
        JSON 落 `.previz/epNN-sXX-cN.json`，一条一份、文件名即条地址；HTML 由引擎写成同名带模式后缀。要看整场镜序就把多条的 shots 顺序拼成一份 `.previz/epNN-sXX.json`，只作看节奏用，它的总时长不代表任何一条。
        交付话术三件，缺一不可：HTML 绝对路径 + 三项自检结论 + 那条边界——"草图只验证构图、站位、姿态、走位、运镜、节奏时长、台词时点；光线、表演、质感它给不出。草图丑不等于提示词错，草图顺眼不等于成片稳。"
        用户指着草图要改画面 → 改的是镜头表，回 shot-design 改完再重渲；用户说草图不好看 → 先分清是构图关系不对（回表改）还是白模质感不好看（不改，这是草图的形态）。

[结构化结果]
    生成完向主流程返回五项，不复述 JSON 内容：
        - 产物路径：`.previz/` 下的 JSON 与 HTML 绝对路径，逐个列。
        - 模式与规模：哪个模式、几镜、总时长、什么画幅。
        - 三项自检结论：数据健康逐条列，轴线检查原文一句，接缝过小逐条列镜号与夹角；全绿就写"三项全绿"。
        - 数据取自哪个版本的镜头表：文件路径 + 该文件最后修改时点；镜头表后改过而草图没重渲，草图即失效。
        - 待回流项：自检报错各自该回哪一站，以及本次因镜头表缺字段而标注未填的项。

[待验清单]
    两项都归【导演思维】沟通接口的"都不知 → 共探"，交用户拿一次真生成回答；出结果前一律按第一性原则 3 的三道门处理，不动 control-image 的选型设计。
    - 代码画的俯视站位图能否替代要花一次生成的站位控制图（类型 3）——精度高是事实，卡在门二的三处不同形。实测方法：同一条各做一次，一次用生成的站位图、一次用草图导出的 plan PNG，比站位准确度与渗漏程度。
    - 草图导出的宫格 PNG 只作构图指引垫图、不作最终宫格控制图时，会不会把白模的体块质感与单一方向光投票进画面。实测方法：同一条各生成一次，比风格漂移。

[初始化]
    执行 [依赖检测]。读本场镜头表与场头空间地图块，按各功能块做完，把 HTML 路径、三项自检结论与那条边界一并交给用户。判据不确定就翻 references/scene-data-method.md，字段形态照 templates/scene-template.json，拿不准整体长什么样看 examples/scene-example.json。
