[定位]
    这是"镜头表 → 三维场景 JSON"的判据库，不是流程脚本。流程在 SKILL.md 各功能块；这里回答"每一个字段怎么填才算对、填错长什么样、对的长什么样"。
    schema 的唯一真相源是 previz.py 的实际实现，本卡是它的只读投影——两处不一致以代码为准，回头修本卡，不在草图里绕过。
    字段形态照 ../templates/scene-template.json，整体长什么样看 ../examples/scene-example.json，那份取自真实镜头表、六模式全渲通过、三项自检全绿，第 6 镜是环绕；外景、单人蹲姿、逐镜姿态覆盖、轴上镜与带 id 的陈设看 ../examples/scene-exterior.json。

[二维时代消失了什么 · 带着旧认知来的人先看这节]
    场景从平面画变成了三维空间，下面六样东西不是改了写法，是不存在了。在旧文档里见过就当没见过：
        两套坐标系（一套侧视一套俯视、y 的含义相反、要人工保持一致）——只剩一套三维坐标，两图一致由物理保证，不必再对。
        `ground` 一个字段兼职编码纵深——拆成 `p[1]` 真实高度与 `p[2]` 真实进深，一个字段不再干两件事。
        裁切窗 `view` / `viewTo` 与各画幅的 `view.w` 上限——画框由摄影机的 `fov` 与位置推出，裁切窗这个概念本身没有了，越界检查随之消失。
        焦段与机位距离一致性检查——视场角物理上就是真的，算不出不一致。
        反打自动镜像——换个机位自然就是反打，翻转 hack 消失。
        `overlay` 画框级遮挡与光斑——三维给真实遮挡，假的不用画了。

[判据卡 · 三维坐标系 · 先认这个，别的都建在它上面]
    怎么认：
        一套坐标，0–100 的立方网格，所有东西都写在里面：**x 左右、y 高度（0 就是地面）、z 进深（大 = 靠近默认机位一侧）**。
        位置一律写成三个数的 `p: [x, y, z]`，尺寸一律写成三个数的 `s: [宽, 高, 深]`。摄影机的 `cam` / `look` 也是同一套坐标里的三个数。
        `figures` 的 `h` 是身高，`stand` 是**站立面的高度**——台阶、踏板、柜台后垫脚的那块板。人站在地上就写 0。
        不追求写实比例。按空间地图块的"居 frame-left/right""高出半头""相隔一张球台的台面宽度"定相对量即可——草图要的是关系正确，不是尺寸正确。
    认错长什么样：
        把 y 当纵深写——这是从二维版带过来的最贵的错。y 是高度，人站在地上 `p[1]` 就是 0，把纵深写进 y 会让所有人浮在半空，而且渲得出来、不报错。
        用 `stand` 编码纵深——`stand` 是台阶高度，进深是 `p[2]`，各归各的字段；混着写会让人凭空长高。
        找"另一套坐标"去填站位——没有另一套。俯视图是这份数据的正交投影，你填一次就够了。
    典型例子：
        掌柜站在柜台后一块四单位高的踏板上、偏画右、靠里：`{"p": [62, 0, 38], "h": 29, "stand": 4}`。
        军官站在地上、偏画左、靠近机位：`{"p": [40, 0, 70], "h": 28, "stand": 0}`。

[判据卡 · meta 四字段]
    怎么认：
        `id` 写条地址 `epNN-sXX-cN`，它同时是导出 PNG 的文件名前缀。
        `title` 写这条在镜头表里的标题原文。
        `track` 写分波字母，与镜头表一致。
        `aspect` 写 `W:H`，**9:16 出竖幅、16:9 出横幅**，取自 visual-style 定的分波画幅。画幅错则一切构图判断全错，引擎不设默认猜测。
        `note` 记两件事：数据取自哪个文件哪个版本，以及哪些字段镜头表没写所以没填。
    认错长什么样：
        竖屏片子写成 `16:9`——每一格的构图判断都是错的，而页面看上去毫无异样。
        `note` 留空——三个月后没人知道这份草图对应的是镜头表的哪一版，草图与表一旦不同步就无从发现。
    典型例子：
        `{"id": "ep01-s01-c1", "title": "雨里进来一个人", "track": "B", "aspect": "9:16", "note": "取自 03-shots/ep01-shots.md 条 1 六镜六字段；镜 3 时长表未写，未填。"}`

[判据卡 · solids · 从空间地图块抽陈设体块]
    怎么认：
        一件陈设一个 `solids` 项：`kind` 给类型、`p` 给中心点、`s` 给三维尺寸，可选 `tone` 与 `label`。
        只抽两种东西：**决定空间关系的**（墙、地、柜台、门、窗——它们定出人在哪个空间里）和**镜头表点了名的**（"齐眉木栅""当票木格架"——它们被写进表里就是因为要拍到）。其余一概不抽。
        栅条不逐根写。`slats: {step, gap}` 交给引擎展开：**step 是栅条间距，gap 是递物窄口的两个 x 坐标 `[起, 止]`**——落在那一段里的栅条自动缩短，窄口就是这么来的。gap 是**开口的范围**，不是缝宽，写成一个数会被拦下。带 slats 的项用 `kind: "slat"`。
        地面写一块比世界略大的 `floor`，墙按需要写；不写地就没有接触参照，所有东西看着都在飘。
    认错长什么样：
        把整个屋子的陈设都搬进来——白模里二十个灰盒子，空间关系反而看不见了。草图不是场景图，是空间关系图。
        用 `s` 的第三个数编码"离机位多远"——`s[2]` 是这件东西自己的进深，位置在 `p[2]`。
        写词表外的 `kind`——引擎静默按灰盒子画，只在数据健康自检里报一行。所以那一行必须读。
    典型例子：
        齐眉木栅：`{"kind": "slat", "p": [50, 25.5, 52], "s": [68, 17, 1.6], "slats": {"step": 6, "gap": [46, 56]}, "label": "齐眉木栅"}`——窄口开在 x 46 到 56 之间。
        当票木格架：`{"kind": "shelf", "p": [62, 30, 20], "s": [30, 22, 3], "label": "当票木格架"}`。

[判据卡 · solids 的 kind 词表]
    怎么认：
        词表以引擎的 `SOLID_KINDS` 为准，三十三个取值，按"它是什么"认，不按"它长什么样"认：
            建筑：wall 墙 / floor 地 / door 门 / window 窗（tone 写 lamp 即窗纸透光）/ curtain 帘 / pillar 柱 / stairs 楼梯 / platform 台阶或踏板 / mirror 镜子 / frame 相框或挂画 / rug 地毯
            家具：counter 柜台 / table 桌 / desk 书桌带侧柜 / chair 椅（带靠背）/ stool 凳 / bench 长凳 / sofa 沙发 / bed 床 / shelf 格架 / cabinet 柜子 / screen 屏幕或电视 / lamp 灯
            环境：plant 盆栽 / tree 树 / rock 石 / vat 缸 / car 车（车头朝 +x）/ cabin 车内舱（车头朝 +x、左舵在 +z 侧，车顶只给监视器看、导演视图从上面看得进去）/ streetlamp 路灯 / animal 猫狗一类的四足动物 / slat 栅条或栏杆（带 slats）/ block 真是方的东西
            基元：sphere 球 / cylinder 柱 / cone 锥 / dome 穹或土丘 / fog 半透明体量（雾、烟、纱、雨幕、光柱）/ water 水面 / statue 人形雕像或假人（可带 pose / arms）——**词表没有的东西用基元拼，不写 block 凑数**：半埋的巨像脸是 sphere 加沙色 dome，沙暴墙是 fog 配 sand，发亮的沙脊是 dome 配 glow
        常用叫法直接写也认，引擎按 `ALIASES` 折到预制件：fridge wardrobe dresser → cabinet，bookshelf rack → shelf，nightstand → table，bar → counter，railing fence → slat，column → pillar，crate box → block，tv monitor blackboard → screen，barrel bin pot → vat，bus truck train → car，armchair couch → sofa，step stage → platform，painting photo → frame，carpet mat → rug，streetlight lamppost → streetlamp，dog cat horse → animal，bush flower → plant，hill dune mound ridge → dome，smoke dust steam mist cloud rain beam → fog，pond pool river sea lake → water，colossus sculpture mannequin → statue，pipe drum → cylinder，tent → cone，ball → sphere。
        每个 kind 是一个预制件：chair 有座有靠背有腿，bed 有床架床垫枕头，window 有框有格心有透光的纸——同一个 kind 在任何场里长得一样，这就是草图跨场、跨模型稳定的来源。
        `rot` 给绕竖轴的旋转角度（度）：椅子朝着桌、车斜停、猫沿墙走都靠它；不写就是正对默认机位一侧。
        任何陈设都可加 `opacity`（0–1，半透明，不投影）与 `glow`（true 或亮度数字，发光）；`floor` 的 `tone` 决定整块地面的颜色——sand 沙、asphalt 柏油、snow 雪、leaf 草、water 水。
        带 `id` 的陈设可以被 look / facing / gaze / axis 引用，也可以做 moves 的主语——轴线立在人与木格窗的连线上、猫沿墙头走到另一端出画，都是这么写的。
        分不清用哪个就用 block——一个诚实的灰盒子好过一个错类型。
    认错长什么样：
        写"书架""货架"这类中文词或词表外的英文——引擎静默按 block 画灰盒子，数据健康自检报一行 `kind 不在词表内` 并把词表印出来，但图照渲。
        为了颜色好看去挑 kind——kind 决定的是这件东西怎么被建起来，颜色调 `tone`。
        把巨像、沙暴、山丘、水面写成 block——那是 statue、fog、dome、water 的活；一场里一半以上陈设是 block，数据健康自检会把它们点名。
        把一面矮墙写成 block——wall 参与"室内还是室外"的判断：三面以上高墙才画天花板，矮墙不算；写成 block 的墙不参与。要硬指定就在 meta 里写 `ceiling: true / false`。
    典型例子：
        当票木格架 shelf；齐眉木栅 slat 加 slats；布门帘 curtain；煤油灯 lamp；粗陶水缸 vat；墙头的黑猫 animal 带 id "cat"；糊纸透光的木格窗 window 带 tone "lamp" 与 id "win"。

[判据卡 · figures · 从空间地图块抽人]
    怎么认：
        一个人一项：`id` 全场唯一的短串、`label` 可视特征代称、`tone` 哑色、`p` 站位、`h` 身高、`stand` 站立面高度、`facing` 躯干朝向、`gaze` 视线落点；可选 `pose` 姿态（stand / sit / kneel / crouch / lie 仰卧 / prone 俯卧，不写即站姿；卧姿的 facing 是头朝哪）、`arms` 手臂（down 垂 / forward 前伸 / hold 抱物 / up 举 / cross 抱胸 / back 背手 / akimbo 叉腰 / point 右手前指，不写即垂臂；左右不同就写 `armL` / `armR`）、`seat` 坐姿时的座面高度（不写按身高的 0.27；席地而坐写 0，腿会伸直）。
        `facing` 与 `gaze` 都写**另一个 id 或一个三维点 `[x, y, z]`**，不写角度——写 id 的好处是人一动，朝向自己跟着对；写角度就得手工重算，而重算漏了不会报错。id 可以是人、焦点物或带 id 的陈设：蹲在缸边朝着缸写 `facing: "vat"`，视线落在自己手里的表上写 `gaze: "watch"`。
        两者可以不同，这正是它们分成两个字段的理由：躯干朝着柜台、眼睛瞟向门口，是一句话就能读懂的表演信息。
        `label` 取 04-assets/reference-index.md 的可视特征代称；那份文件缺就写镜头表里的代称，**不写 @编号**——草图不是提示词。
    认错长什么样：
        `facing` 写成角度数字——引擎认 id，写数字等于没写。
        `id` 与 `axis`、`gaze`、`moves.who`、`shots.look` 里用的串对不上——引用方静默失效，越轴与接缝检查跟着空转。数据健康自检会报 axis 的那一处，但 `gaze` 指向不存在的 id 只是不画线，不报。
        把群演一个个写进来——白模里五个色块反而分不出主次，群演合成一个 grey 或干脆不写。
        把蹲着的人写成站着——`pose` 不写默认站姿，全场坐着谈判的戏会整场站起来，而且不报错；镜头表写了蹲、坐、跪、卧，就要写 pose。
        某一镜里他站起来、回头了，去改 figures 母项——那是全场的默认状态；单镜的变化写进那一镜的 `figures` 覆盖（见六字段那张卡）。
    典型例子：
        `{"id": "boss", "label": "掌柜", "tone": "amber", "p": [62, 0, 38], "h": 29, "stand": 4, "facing": "off", "gaze": "off"}`
        `{"id": "boss", "label": "老掌柜", "tone": "amber", "p": [52, 0, 52], "h": 29, "pose": "crouch", "arms": "hold", "facing": "vat", "gaze": "watch"}`——蹲在缸边、双手抱在胸前、脸朝缸、眼睛看手里的表。

[判据卡 · focus 与 axis]
    怎么认：
        `focus` 是视觉焦点小物——被镜头表点名要拍的那件东西：怀表、刀、一张纸。写 `id` / `label` / `tone` / `p` / `r` 半径；可选 `shape`（disc 圆盘如怀表 / box 方块如手机、纸、相机 / ball 球 / stick 棍如刀、笔）、`s` 明确尺寸 [宽, 高, 深]、`rot` 转角。它比 solids 小、比 solids 重要，所以单独一类：它能当 `look` 的目标、能当 `moves` 的主语。
        `axis` 是 180° 轴线，写两个端点的数组——通常是对戏的两个人的 id；单人场对着一个地标的戏，另一端可以写焦点物或带 id 的陈设的 id，也可以直接写一个点 `[x, y, z]`（老掌柜与前堂木格窗的连线：`["boss", "win"]`）。机位离线不到两个单位算骑在轴上，不算越轴。**两人以上的对手戏必须声明**——不声明，越轴检查与接缝检查两项同时空转，而页面看上去一切正常。
    认错长什么样：
        把每件道具都塞进 focus——focus 是"这一条要拍它"，不是"场里有它"。场里有的进 solids。
        `axis` 写了但 id 拼错（`["boss","officer"]` 而 figures 里是 `off`）——数据健康自检会报 `axis 指向不存在的 id`，读到就改，别跳过。
        单人场硬凑一条轴线——单人场本来就没有轴线，不写即可，自检不报。
    典型例子：
        `focus: [{"id": "watch", "label": "怀表", "tone": "gold", "p": [51, 17.6, 52], "r": 1.4}]`；`axis: ["boss", "off"]`。

[判据卡 · 六字段 → shots 各槽的对应]
    怎么认：
        逐镜六字段与 shots 的槽是一一对应的，照搬不解释：
            镜号 → `n`　　镜头标题 → `title`　　景别 → `framing`　　时长 → `dur`（秒，裸数字）
            节奏 → `pace`　　台词或音效时点 → `beat`　　【镜头语言】整句原文 → `lens`
        另有三个只上字幕、不参与任何计算的槽：`title` 镜头标题（宫格、关键帧、放映三个页面都拿它当字幕）、`move` 运镜的一句话标签（放映页侧栏显示）、`at` 关键帧页的帧标。
        `move` 与 `at` 不填时引擎会兜底——`move` 按有没有 orbit / to 猜一句、`at` 按镜号写「第 N 帧」。兜得出来但不如镜头表的原话准，能填就填。
        `lens` 与 `title` 都抄原文，一个字不改。页面把它与译出的摄影机数据并排显示，就是给人核对"这一句译对没有"用的——改了原文，这个核对就失效了。
        【导演意图】的情感行压成一句进 `intent`。
        两个只在个别镜里出现的槽：`figures` 覆盖——`{"boss": {"pose": "stand", "gaze": "win"}}`，这一镜里谁的姿态、手臂、朝向、视线与全场默认不同就写谁，只写变了的那几项；`onAxis: true`——镜头表明写了轴上镜或骑轴中性镜的镜才写，它让这一镜不参与越轴投票、也不被报。
        镜头表没写的字段不填。缺景别就不写 `framing`，缺时长就不写 `dur`，在 `meta.note` 里记一笔。
    认错长什么样：
        把 `lens` 顺手改通顺了——它是被核对的对象，不是被润色的对象。
        `title` 留空——宫格与关键帧两页的字幕就是空的，导出给用户看时没人认得出哪格是哪镜。
        `dur` 写成 `"3.5"` 字符串——总时长会算错。
        镜头表没写时长就估一个填进去——草图从此变成第二份未经确认的镜头表，而且没人知道那个数是估的。
        把 `onAxis` 当免死金牌——镜头表没标、只是想让越轴警告消失就写 true，这是篡改证据，与挪机位凑角度是同一种错。
    典型例子：
        `{"n": 1, "title": "表落柜台", "framing": "大特写", "dur": 2.5, "pace": "静", "beat": "雨声压过来", "lens": "长焦大特写锁死怀表，机位不动", "move": "锁定机位 · 无漂移", "at": "第 1 帧", "intent": "先让观众看清这块表值多少"}`

[判据卡 · 摄影机三形态 · 静止 / 插值 / 环绕]
    怎么认：
        摄影机是数据，只有三种形态，都写在同一套三维坐标里：
            **静止**——`cam` 机位 + `look` 看点 + `fov` 视场角。三样定死一个画面。镜头表写"锁定机位"就只写这三样。
            **两点插值**——在静止的基础上加 `to`（机位终点）、`lookTo`（看点终点）、`fovTo`（视场角终点）中的任意几样，加 `moveEase` 给速度质感（`linear` 匀速 / `out` 先快后缓 / 不写则两头缓中间快）。
            **环绕**——`orbit: {center, r, from, to, y}` 加 `look`。摄影机沿以 center 为心、r 为半径、y 为高度的圆弧，从 from 度走到 to 度。**这一类二维画不出来**，它是三维化的直接理由。
        推拉摇移升降不是五种特例，是同一套插值的不同分量在动：
            推近 → `fov` 变小，或 `cam` 朝 `look` 方向走（两者画面不同——变 fov 是变焦、动 cam 是移动摄影机，镜头表写哪个就写哪个）
            拉远 → 反过来
            摇 → `look` 变而 `cam` 不变
            横移 / 升降 → `cam` 变而看的方向跟着走
            希区柯克变焦 → `cam` 与 `fovTo` 反向同时变，三维里这一条现在渲得出来了
        `look` 可以写坐标，也可以写一个 figure 或 focus 的 id——写 id 的好处同 `facing`：主体一动，摄影机自己跟上。
    认错长什么样：
        先在草图里挑一个好看的运镜，再回头改镜头表——**方向永远是镜头表 → 草图**。这是拿投影反过来改真相源，画面层的所有权在镜头表不在这里。想改运镜回 shot-design 改表，再重渲。
        环绕写成一串手工插值点——`orbit` 就是为这个存在的，手写点位既算不准角度，接缝检查也读不出这是运动镜。
        某镜既没有 `cam` 也没有 `orbit`——这一镜没有摄影机，画不出来，数据健康自检会报。
        `fov` 缺或写成 `"18"` 字符串——引擎按 40° 兜底，景别判断整条失真；自检会报，读到就改。
    典型例子：
        静止：`{"cam": [58, 26, 62], "look": [51, 17.6, 52], "fov": 18}`
        环绕：`{"orbit": {"center": [51, 20, 52], "r": 34, "from": 210, "to": 310, "y": 24}, "look": [51, 17, 55], "fov": 47}`

[判据卡 · fov 就是景别 · 镜头语言写焦段时怎么换算]
    怎么认：
        `fov` 是**水平视场角**，单位度。镜头表【镜头语言】写的是焦段（"85mm 长焦"）时，按全画幅换算：**fov = 2 · arctan(18 / 焦段毫米数)**。常用档：
            24mm → 74°　　35mm → 55°　　50mm → 40°　　85mm → 24°　　135mm → 15°
        镜头表只写景别不写焦段时，按这个梯子取：全景 70–80° / 中全景 45–55° / 中景 40–50° / 近景与过肩 25–32° / 特写 18–24° / 大特写 14–18°。
        景别是 fov 与机位距离**共同**决定的，不是 fov 单独决定的：同样 47°，机位退远就是中全景、贴近就是近景。所以 `framing` 那一栏写的是镜头表的原话，`fov` 写的是达成它的手段，两者一起看才对。
    认错长什么样：
        照抄焦段数字当 fov——把 `fov: 85` 写进去，那是一个 85 度的超广角，与镜头表要的 85mm 长焦正好相反。这个错渲得出图、不报错，是本卡最贵的一条。
        为了"让画面里多装点东西"把 fov 调大——景别就变了，而 `framing` 那一栏还写着原来那个词，草图与镜头表从此不是一回事。
    典型例子：
        "长焦大特写锁死怀表" → `fov: 18`，机位贴近到 12 单位外。
        "广角全景交代整个前堂" → `fov: 76`，机位退到墙边。

[判据卡 · moves · 走位]
    怎么认：
        `moves` 是镜内位移：`who` 写 figure 或 focus 的 id、`from` 与 `to` 各写三维偏移量、`t: [起, 止]` 写在这一镜里占哪一段（0 到 1 的归一化时间）。
        偏移是**相对这个人自己的 p 的位移**，不是绝对坐标——所以 `from: [0,0,0]` 就是"从他站的地方开始"。
        只做移动，不做表演。抬手、转头、皱眉一概不写——白模给不出，写了会让人拿白模的"表演"去评判一条还没生成的戏。
    认错长什么样：
        用 `moves` 表达表演——见上。
        `who` 指向不存在的 id——静默不动，不报。渲完发现人没走就查这里。
        整条戏的调度写成一个 move——`moves` 是镜内的，跨镜的位置变化写成下一镜里那个人不同的 `p`。
    典型例子：
        怀表被推进画：`{"who": "watch", "from": [-9, 0, 4], "to": [0, 0, 0], "t": [0, 0.55]}`
        军官在环绕镜的后半段退开：`{"who": "off", "from": [0, 0, 0], "to": [-3, 0, 6], "t": [0.45, 1.0]}`

[判据卡 · 哑色板 · 与控制图站位图同源]
    怎么认：
        `tone` 给人物用五色：amber 哑橙 / blue 哑蓝 / green 哑绿 / rose 哑玫 / grey 哑灰，另有 gold 哑金给焦点物。不填按 grey。solids 另有木色、帘色一类的材质色，词表以引擎的 `TONE_RAMP` 为准。
        规则与 control-image 站位图那一套同源：**一人一色、全场固定、色彩只做身份**。色不是服装，不是情绪，不是重要性排序。
        选色只有一条判据：同框的人色相拉满距离，一眼分得开。两人对戏用 amber + blue，加第三人 green，第四人 rose，群演 grey。
    认错长什么样：
        按角色服装配色——"他穿蓝袍所以用 blue"，等于把服装信息塞进一个只负责身份的槽，下一场换了衣服就得改色，跨场认不出人。
        用色表达"谁是主角"——重要性靠构图与景别表达，不靠颜色。
        同框三人用 amber、gold、rose——色相挤在暖端，缩略图上分不开。
    典型例子：
        掌柜 amber、军官 blue、怀表 gold——两人一暖一冷，物件用金跳出来。

[判据卡 · 白模形态 · 导演台三维白模，灯只为分体块]
    怎么认：
        引擎在浏览器里用 WebGL 实时渲染：一盏工作室灯（主光 + 补光 + 环境光）带真实投影，地面网格给距离参照，关节人偶有头、躯干、四肢、脚，陈设是按 kind 拼出来的预制件。play 页多一个导演视图，可以自由环视、俯视、站到当前机位肩后看它与被摄者的关系。
        这盏灯**只为分清体块与遮挡关系，不是布光**。光向是引擎定死的常数，场景 JSON 不写、也写不了。
        白模只表示体量、姿态、朝向与遮挡，不表示布光、材质与表情。人偶没有脸——这是刻意的：有脸的白模会被当成表演去评判。
    认错长什么样：
        试图在场景 JSON 里布光——没有这个字段。光影氛围归分镜图阶段，草图这一层不碰。
        因为立体、精细了就把白模当"快真了"去评判画面质感——**越像成片，越要守住这条边界**。草图验证空间、姿态与节奏，不验证光、表演、质感。
        拿导演视图或俯视的截图去投喂——它们带机位、取景锥与标签，是给人看的工作视图；能投喂的只有监视器一侧的帧，而且还要过三道门。
    典型例子：
        当铺前堂：栅条的影落在柜台面上、军官的体块挡住身后的门帘——这两件是遮挡关系，读得出来；柜台木头是什么成色、煤油灯把人脸打成什么样——这两件读不出来，也不该从草图里读。
        当铺后院：老掌柜蹲在缸边、背朝透光的木格窗，猫在墙头——空间关系与姿态读得出来；月光有多冷、缸面映不映得出月亮——读不出来。

[三项自检 · 报错回哪一站修]
    三项自检是本 skill 精准度的全部来源。跑一次命令，终端就报完，逐条读。
    **总纪律：除数据健康外，草图报错指向的是镜头表的问题，不是草图的问题。** 改 JSON 把警告消掉是篡改证据——把机位挪回轴同侧，成片照样越轴。

    1 · 数据健康，分两档
        **[拦下] 档——会让引擎崩的写法**：任何坐标位不是三个数字（`p` / `s` / `cam` / `look` / `to` / `lookTo` / `orbit.center`），或 `h` / `r` / `dur` / `fovTo` / `orbit` 的各数值位不是数字。绝大多数情况就是母版占位符没填完。
            引擎**拦在渲染之前，退出码 2，已有产物一个字不动**——不甩 traceback，也不会把上一次的好草图截成空文件。
        **提醒档——渲得出图但图是错的、或另外两项自检在空转**：kind 不在词表、figures 或 focus 缺 id、既没 h 也没 r、两人以上没声明 axis、axis 指向不存在的 id、某镜没有摄影机、某镜缺 look、某镜缺 fov。
        报什么：`⚠ 场景数据有 N 处会让自检空转或画错——「没报错」不等于「全绿」：` 加逐条，会崩的那些前面标 `[拦下]`。
        回哪修：**就在本站补数据**。它报的是这份 JSON 写漏了，不是镜头表错了——这是三项里唯一不回流的一项。
        为什么提醒档也必须存在：`没报错` 不等于 `全绿`。两人对戏却漏写 axis，终端安静得像一切正常，实际越轴与接缝两项一次都没跑。这个判据不能留给人记，所以做成自检。

    2 · 轴线检查
        怎么算：叉积算每个机位落在 180° 轴线哪一侧，取多数侧为守轴侧，少数侧的镜号报出来，场记平面图上标红，页面给结论。轴线取自 `axis`。
        报什么：`轴线检查：镜 4 在轴线另一侧　⚠ 若非刻意越轴，改机位或走合法越轴路径`。全绿时是 `N 镜全部在轴线同侧，守轴成立`。
        回哪修：回 shot-design。两条路——改机位回到同侧；或确要越轴，按 blocking 的 [判据卡 · 越轴的四条合法路径] 选一条走：条内可见的运动越轴 / 中性骑轴镜缓冲 / 主体移动重立轴线 / 插入镜缓冲；越完把它写进本场场级空间地图块的「排布变化」行、带镜号，此后方位词按新轴。真相源在 blocking 的 axis-and-coverage.md。
        注意平票：机位两侧各半时，引擎取其中一侧为准、把另一半报成越轴。这种场面本身就是空间没定，回表定清楚哪一侧是主。
        注意过肩对打：一对过肩正反打的两个机位必须在轴线同侧。觉得"过肩本来就该在两边"是最常见的直觉错误——两边那是越轴。

    3 · 接缝检查
        怎么算：见下一张卡。
        报什么：`⚠ 接缝夹角过小，会读成跳切：镜 1 → 镜 2：夹角 22°，低于 30°`。
        回哪修：回 shot-design，调机位角度或调景别差，改一样即可。

[判据卡 · 接缝检查 · 30° 规则与两条豁免]
    怎么认：
        算相邻两镜的机位在**被摄者处**张开的夹角。低于 30° 时，观众读不出这是换了机位，只读出画面"跳了一下"——这就是跳切。
        三条豁免，命中任一条就不报：
            **切入的是运动镜**——下一镜是环绕、是插值运动、是变焦，运动本身打断了读感，小夹角不再读成跳切。
            **景别跨两档以上**——两镜 fov 比值达到 2 倍，尺寸变化本身就把两个画面区分开了。
            **换了被摄者**——两镜的看点相距超过十二个单位，切到另一个主体不是跳切。
        这个数二维算不出来：二维没有摄影机，只有裁切窗，两个裁切窗之间张不开角度。**它是三维化顺带拿到的一项新自检**，不是原有能力的翻新。
        `-m cut` 模式逐缝把这件事画出来：每一缝给出点画面、入点画面与夹角，一眼看得出是哪两镜的问题。
    认错长什么样：
        把机位挪几个单位把角度凑过 30°——凑过去了，成片里那一刀照样跳，因为镜头表没改。
        以为豁免是"可以不管"——豁免是"这一缝不构成跳切"，不是"这一缝随便"。
        以为 30° 是硬阈值——它是读感的经验值，报出来是让人看一眼，不是判死刑。刻意要跳切感的地方，看完就放过。
    典型例子：
        镜 2 中全景双人 → 镜 3 全景建立镜头，夹角 24°，但 fov 47 → 76 不到 2 倍、镜 3 是静止镜——报，回表把镜 3 机位往侧面挪。
        镜 5 过肩 → 镜 6 环绕，夹角 9°——不报，镜 6 是运动镜，命中豁免一。

[六模式与交付物的对应]
    模式不是随便切的视图。前四个一个模式对一类真实交付物；后两个是工作视图，给导演自己看的，不对应任何交付物。按"要预览哪个交付物"选，不发明新模式。

| 模式 | 命令 | 对应什么 | 页面上看什么 | 导出什么 |
|---|---|---|---|---|
| play | `-m play` | 06-motion-prompts 的视频条提示词 | 导演台：左栏镜头列表与自检，中间可自由环视的导演视图（全部机位、取景锥、轨迹、轴线、视线、走位；自由环视 / 俯视 / 机位肩后三种预设），右栏本镜监视器与规格，镜头语言原文与译出的摄影机数据并排 | 当前帧 / 全部帧 / 宫格图 / 导演视图 |
| grid | `-m grid --cols N` | 宫格控制图（类型 2） | 画面就是那张宫格图本身的样子 | 整张宫格图 / 拆成单格 |
| keyframes | `-m keyframes` | 关键帧序列控制图（类型 1）；只有一帧时即单张分镜 | 逐帧构图，帧间数字是该帧到下一帧的时长 | 全部关键帧 / 拼成宫格图 |
| plan | `-m plan` | 站位图控制图（类型 3） | 交付物本身：谁在哪、躯干朝向、视线、走位、地标 | 站位图 |
| stage | `-m stage` | 工作视图，不是交付物 | 垂直俯视的场记平面图：全部机位、每台机器的覆盖扇形、视线、环绕弧、轴线 | 场记平面图 PNG |
| cut | `-m cut` | 工作视图，不是交付物 | 逐缝：出点画面、入点画面、夹角、越没越轴 | 无 |

    **stage 与 plan 同为垂直俯视，分工不许混。** stage 带机位、带镜号景别，是给导演审覆盖的工作视图；plan 只画站位，是交付物。一张图干两件事就两件都不成立——要看机位分布用 stage，要交付站位图用 plan。
    stage 为什么是垂直俯视而不是抬高的透视：透视会遮挡、会压缩距离，覆盖冗余（几台机器都在拍同一块）与覆盖空洞（没人拍的那块）两件事都看不出来，标注也没地方放。俯视图上扇形的张角就是那台机器的实际视场角，重叠与空白直接读得出来。
    同一份 JSON 六模式都能渲，选错重跑一次即可、不必改数据。要连着看就都跑，`-o` 各给一个名字。
    控制等级可以直接当选型信号：L1 → play；L2 → keyframes；L3 → plan；L2 且要批产候选帧 → grid；L4 → stage 看机位分布与动线。
    L4 空间动线这一档在三维版里不再是短板：环绕、穿行、长运动都渲得出来了，`orbit` 与插值各管一类。真渲不出的只剩手持抖动与移焦这两样——它们不是空间问题，是质感问题，留在 `lens` 原文里、`note` 记一句。

[导出图当参考图投喂 · 用法与边界]
    怎么认：
        下载是全客户端 WebGL 画布→PNG，短边 1080，与平台参考图常用尺寸对齐；站位图与场记平面图是 SVG→PNG。
        合法用法，按把握从高到低：
        1 · 给人看的沟通稿——表确认时甩给用户对齐构图与站位。这一档零风险，永远合法。
        2 · 写控制图生成提示词时的构图依据——人对着草图写 control-image 的提示词，图本身不进任何提示词。这一档也零风险。
        3 · 当参考图投喂——要过三道门。三道门都是 control-image 与 spatial-map-template 的既有防渗规则，本卡只读引用、不新立：
            门一 · 帧类控制图必须嵌 visual-style 的通用基准段与本场域的场域锚句，草图两层都没有——直接投喂等于让一组白模体块与一个方向光参与风格投票。
            门二 · 站位图母版要求白底、极淡网格、细轮廓、无填充、图上零文字字母；草图 plan 导出是深底、实心色块、带中文标签，三项都不同形。
            门三 · 俯视规划图按 spatial-map-template 现行规则标「人用规划 · 勿投喂」，不进条头【上传清单】、不被【参考资产绑定】@。草图的 plan 与 stage 导出都与它同类。
        没过门的图停在第 1、2 档用，一样有价值。
    认错长什么样：
        把 grid 导出的宫格 PNG 直接塞进条头【上传清单】当宫格控制图——它没有基准段、没有场域锚句，投喂进去是一次风格污染，比不做控制图更贵。
        把 plan 或 stage 导出的 PNG 当站位图 @ 进【参考资产绑定】——图上的中文标签会被渲染进画面，这是站位图头号废镜形态。
        因为立体了看着像样就觉得可以投喂了——**立体只是让空间关系可读，三道门一道也没松**。
        因为"代码画的更准"就去改 control-image 的选型——精度高是事实，能不能替代是待验项，见 SKILL.md [待验清单]，实测出结果前不动它的设计。
    典型例子：
        表确认时导出宫格图给用户看镜序 → 用户指着镜 3 说构图不对 → 回 shot-design 改镜头表 → 重渲 → 用户点头 → control-image 照镜头表正常出宫格控制图，草图那张不进流程。
