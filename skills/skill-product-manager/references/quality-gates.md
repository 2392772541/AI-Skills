# 高质量 Skill 质量门禁

本门禁用于创建、升级、引入和评审 Skill。核心原则：**描述让 Agent 找到 Skill，正文让 Agent 无法跳过关键步骤，验证让人能证明任务真的完成。**

## 1. 发现契约（Discovery Contract）

- `name` 与目录名一致，使用小写连字符。
- `description` 先写做什么，再写 `Use when` 或等价的明确触发条件。
- description 不复述完整步骤，避免 Agent 只按摘要行动。
- 至少准备 3 个真实正向表达和 2 个相邻任务负向表达。
- priority 只能在触发词或 pattern 命中后加分，不能凭优先级抢占无关请求。

## 2. 适用边界（Scope Boundary）

正文必须回答：

- 什么时候使用？
- 什么时候不使用？
- 与相邻 Skill 如何分工？
- 缺少什么信息时必须停下来问？什么信息可用可逆默认值继续？

## 3. 强制工作流（Enforced Workflow）

- 核心步骤有明确顺序、输入、产物和出口条件。
- 能脚本化的确定性检查交给脚本，不靠“请认真检查”。
- 每个阶段写明失败时如何回退、重试或缩小范围。
- 对长任务写检查点；对修改任务写 diff 和回滚路径。

## 4. 反偷懒设计（Anti-Rationalization）

至少记录 3 类常见借口及反证，例如：

| 常见借口 | 反证/强制动作 |
|---|---|
| “改动很小，不用测试” | 小改动最容易被复制扩散；至少运行最小回归或语法检查 |
| “先实现，稍后补规格” | 未定义验收标准会导致返工；先写最小契约再动手 |
| “看起来已经好了” | 视觉或单次成功不等于业务链路通过；必须按最终使用路径验证 |
| “用户很赶，跳过门禁” | 时间压力是行为 eval 的必测场景，不是绕过理由 |

同时列出可观察红旗：未读现有文件就重建、未运行测试却写“通过”、只给计划不落地、把警告数说成零、输出存在但业务流未验证。

## 5. 证据化完成标准（Evidence-based Definition of Done）

每个完成项必须对应证据：

- 代码：测试命令、退出码、diff、关键文件路径。
- 数据：输入/输出行数、去重数、抽样或哈希。
- 媒体：源文件哈希、输出参数、可播放性和用户风格验收分开报告。
- 系统：运行时状态、实际请求/业务作业，而不只是窗口已打开。
- 外部写入：真实 API 返回和对象 ID；未执行的写入只能标记 partial。

## 6. Eval 四层模型

1. **结构层**：frontmatter、名称、链接、脚本语法、目录自包含。
2. **路由层**：正向 prompt 应进入 top-k；负向 prompt 不应误触发；检查近似 Skill 冲突。
3. **行为层**：在临时 fixture 上让 Agent 真正执行，按 expectations 检查产物和工具调用。
4. **压力层**：加入时间压力、沉没成本、权威指令、失败重试等诱导，验证核心门禁仍生效。

行为 eval 的 expectation 必须描述可观察行为，而不是要求复述某句话。

## 7. 可移植性

- Skill 单目录复制后仍能解析所有本地链接。
- 共享 references 若位于仓库根目录，必须在单 Skill 安装方案中复制、内嵌或明确降级。
- Shell 命令要考虑 Windows/Linux 路径分隔符、编码和可用性。
- 不为对称而创建空目录；大于约 100 行的参考资料再按需拆分。
